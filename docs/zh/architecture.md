# 架构

## 概览

hoshilet 是一个单进程、单机的应用，由以下几个部分组成：

| 组件 | 位置 | 说明 |
|------|------|------|
| 后端服务 | `cmd/hoshilet-server`、`internal/platform` | Go HTTP 服务：认证、API、上传、部署 |
| ZIP 校验器 | `internal/archive` | 沙箱子进程，安全地校验和解压归档 |
| 管理界面 | `web/` | React SPA，独立构建，由反代提供服务 |
| CLI 工具 | `cli/npm/`、`cli/python/` | 两套可互换的 CLI 客户端，使用同一套 HTTP API |

Go 二进制和管理界面是独立构建和部署的。后端永远不会提供前端资源——那是反代的工作。

## 数据层

后端使用 SQLite WAL 模式。每个新连接都会设置 `foreign_keys`、`busy_timeout` 和 `FULL synchronous`。进程级 `flock` 防止多个实例同时访问同一数据目录。

控制面的修改（项目设置、用户管理等）通过互斥锁串行执行。上传和解压可以并发进行，不持有这个锁——只在提交阶段短暂获取，此时会重新检查权限并比较项目 revision。

数据库只有一个连接。事务内的所有查询必须通过 `tx.Query`/`tx.Exec`，不能用顶层的辅助方法。

## 部署流程

用户上传 ZIP 时，经历以下步骤：

1. **暂存：** 文件解压到私有 staging 目录，校验后 fsync。
2. **记录：** 事务写入 Deployment、Upload 和「发布意图」。
3. **链接：** 创建相对符号链接，原子 rename 到 `public/namespace[/project]`，fsync 父目录。
4. **提交：** 第二个事务更新当前版本、递增 revision、记录 ActivationEvent、删除意图。
5. **清理：** 执行保留策略——超出保留数量的旧版本标记为待删除，宽限期后清理文件。

### 崩溃恢复

启动时（以及之后每分钟），服务会查找未完成的发布意图并重新执行。已经提交的 ActivationEvent 不会重复生成。恢复还会对账公开链接、完成待处理的删除、清理 staging 残留。

如果某个项目有未完成的意图，该项目的新写入会被阻塞——防止旧意图覆盖新数据。

### 版本生命周期

- **保留中的版本**可以回滚。
- **已淘汰的版本**不能再激活，文件在宽限期后删除。
- 当前版本和正在部署中涉及的版本永远不会被清理。

上传时间用秒级 UTC Unix 时间戳。每次激活（包括回滚）都会追加一条事件记录。

## Namespace 模型

在一个 namespace 里创建的第一个项目决定了它的模式：

- **根站点模式：** namespace 本身就是站点（内部用空项目名，但仍然有项目 ID）。
- **子项目模式：** 一个 namespace 下有多个命名项目。

两种模式互斥。删除所有项目后才能切换。

URL 使用名称（`/~team/docs/`），但权限绑定的是不可变的 ID。删除再重建一个同名项目，不会继承旧项目的 API Key 或 OIDC 信任。

## OIDC 信任规则

每条信任规则绑定 issuer + GitLab 项目 ID + 分支和 tag 白名单。一条规则里的所有条件必须同时满足——不能跨规则组合权限。

- 分支和 tag 独立匹配：支持精确名称和 `*` 通配符（零个或多个字符，包含 `/`）。空列表禁止该类型发布，单独的 `*` 允许该类型的所有引用，其他字符按字面匹配。
- `require_ref_protected`（默认关闭）：严格检查 token 的 `ref_protected` claim。
- `allow_mr_pipelines`（默认关闭）：仅限同仓库 MR，按来源分支匹配。跨 fork 的 MR 始终拒绝。

短期凭据绑定到匹配的 trust ID。删除信任规则会立即撤销其发布能力。

## 服务端消息

实例消息通过保留 `ResponseController.Unwrap` 的响应包装器注入。`X-Hoshilet-Server-Message` 响应头只在最终 2xx 状态时添加。CLI 在解析 JSON 响应体和检查状态码之前就会校验和显示消息。

## 后台任务

维护任务（恢复、清理）会把数据库辅助函数的 panic 转换为 error，记录失败日志，下一轮继续执行。
